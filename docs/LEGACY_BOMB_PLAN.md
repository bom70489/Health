# Checkin — เครื่องมือ ขอบเขตงาน และแผนพัฒนา Hackathon 20 วัน

> โรงพยาบาลสร้างนัด ผู้สูงอายุเปิดดู รับการเตือน และฟังรายละเอียด โดยมี AI “กรร” ช่วยตอบคำถามเกี่ยวกับนัด

- หัวข้อ: **4. Health & Aging Society**
- ช่วงพัฒนา: **16 ตุลาคม–4 พฤศจิกายน 2026 (พ.ศ. 2569)** รวม 20 วัน
- เขตเวลาที่ใช้: **Asia/Bangkok**
- ฉบับปรับปรุง: 7 ตุลาคม 2026 ตามข้อสรุปล่าสุดของทีม
- เป้าหมาย: ต้นแบบ Android ที่เดโมได้ครบเส้นทาง พร้อมข้อมูลผู้ป่วยสมมติ
- บริบททีม: มีผู้พัฒนาหลัก 1 คนที่เคยเขียน React ทีมมีพื้นฐาน TypeScript และ Java แต่เพื่อนคนอื่นยังไม่เคยเขียน React จำนวนสมาชิกและเวลาว่างต่อวันยังไม่ยืนยัน
- แผนนี้เป็นประมาณการ ต้องประเมินใหม่จากผลงาน 3 วันแรก ไม่ใช่การรับประกันว่าจะเสร็จใน 20 วัน

## 1. ข้อสรุปล่าสุดที่ให้ยึด

ทำ **แอปเดียวด้วย React Native + Expo + TypeScript** ใช้ Supabase เป็นระบบหลังบ้านและฐานข้อมูล Login หน้าเดียวแล้วเปิดหน้าตามบทบาทผู้ป่วยหรือเจ้าหน้าที่

**ไม่มีเว็บเจ้าหน้าที่แยก ไม่มี Flutter และยังไม่เพิ่ม Java/Spring Boot ในรอบนี้** เพื่อให้คนพัฒนาหลักดูแลเทคโนโลยีจำนวนน้อยลง ข้อเสนอนี้แทนโครงสร้างเดิมที่เคยแบ่ง mobile และ admin-web

เส้นทางหลัก:

```text
เจ้าหน้าที่ Login → เลือกผู้ป่วย → สร้างนัด
                                  ↓
ผู้ป่วย Login → ดูนัด → ฟังรายละเอียด → รับทราบ → รับการเตือน
                                  ↓
                       ถามกรรเรื่องข้อมูลนัด
```

โรงพยาบาลเป็นผู้ให้ข้อมูลผ่านหน้าเจ้าหน้าที่ของต้นแบบ ผู้ป่วยไม่ต้องกรอกนัดหรือถ่ายเอกสารเอง แต่ยังไม่ได้เชื่อมกับระบบโรงพยาบาลจริง หากใช้งานจริงแล้วต้องกรอกซ้ำ จะเพิ่มภาระเจ้าหน้าที่ จึงต้องหารือเรื่องเชื่อมระบบเดิมกับโรงพยาบาลในระยะถัดไป

## 2. ปัญหาและกลุ่มผู้ใช้

- ผู้ใช้หลัก: ผู้สูงอายุที่มีนัดติดตามและต้องการดูข้อมูลโดยไม่ผ่านหลายขั้นตอน
- ผู้ใช้ฝั่งสถานพยาบาล: เจ้าหน้าที่ที่สร้าง แก้ไข และยกเลิกนัด
- คุณค่าที่ต้องพิสูจน์: ผู้ป่วยหาวันนัด สถานที่ และคำแนะนำได้ง่ายขึ้น โดยมีเสียงช่วยอ่าน
- ต้นแบบช่วยเรื่องข้อมูลและการเตือนนัด ยังไม่ได้แก้คิวหน้างานหรือรับประกันว่าไม่ต้องรอพบแพทย์
- การมีเสียงไม่ได้หมายความว่ารองรับผู้พิการทุกกลุ่ม ต้องมีข้อความและปุ่มควบคู่กัน

## 3. เครื่องมือที่จะใช้

| ส่วน | เครื่องมือ | หน้าที่และเหตุผล |
|---|---|---|
| ภาษาหลัก | TypeScript | ใช้ทักษะเดิมกับหน้าจอและฟังก์ชันเซิร์ฟเวอร์ |
| แอป | React Native | สร้างหน้าจอและพฤติกรรมแอปมือถือ |
| เครื่องมือพัฒนาแอป | Expo | จัดการโปรเจกต์ รัน ทดสอบ และสร้างไฟล์แอป |
| เปลี่ยนหน้า | Expo Router | แยกหน้า Login ผู้ป่วย และเจ้าหน้าที่ |
| ฐานข้อมูล | PostgreSQL บน Supabase | เก็บผู้ใช้ นัด อุปกรณ์ และประวัติส่งแจ้งเตือน |
| เข้าสู่ระบบ | Supabase Auth | จัดการบัญชีและ session ไม่เก็บรหัสผ่านเอง |
| สิทธิ์ข้อมูล | PostgreSQL Row Level Security (RLS) และสิทธิ์การแก้ไขที่จำกัด | ป้องกันดูข้อมูลข้ามบัญชีและแก้ไขเกินบทบาท |
| โค้ดฝั่งเซิร์ฟเวอร์ | Supabase Edge Functions | ตรวจผู้ใช้ เรียก AI และส่งแจ้งเตือน |
| งานตามเวลา | Supabase Cron | เรียกงานตรวจนัดที่ถึงเวลาเตือน ต้องตั้งค่างานนี้จริง |
| แจ้งเตือน | expo-notifications + Expo Push Service | ลงทะเบียนอุปกรณ์และรับ Push Notification |
| อ่านออกเสียง | expo-speech | อ่านข้อมูลนัด ต้องลองเสียงภาษาไทยบนเครื่องเดโม |
| AI | API โมเดลสำเร็จรูป 1 ผู้ให้บริการ | ตอบจากข้อมูลนัด ไม่เทรนโมเดลเอง ผู้ให้บริการยังไม่เลือก |
| จัดการโค้ด | Git + GitHub | เก็บประวัติและรวมงานทีม |
| เครื่องมือเขียนโค้ด | VS Code หรือโปรแกรมที่ถนัด | ไม่ต้องเปลี่ยน editor หากใช้งานเดิมคล่อง |
| สร้างแอปทดสอบ | Expo development build ผ่าน EAS Build หรือ build ในเครื่อง | เลือกวิธีเดียวที่ทีมตั้งค่าได้สำเร็จ |
| ทดสอบ | มือถือ Android จริง | ตรวจเสียง สิทธิ์แจ้งเตือน การล็อกจอ และการสลับบัญชี |

### Expo คืออะไร

TypeScript คือภาษา, React Native ใช้สร้างแอป, Expo เป็นเครื่องมือช่วยพัฒนาและสร้างแอป ส่วน Supabase เป็นระบบหลังบ้าน

- **Expo Go:** ใช้ทดลองหน้าจอเบื้องต้นได้เร็ว แต่ไม่เพียงพอสำหรับทดสอบ remote push ของโครงการนี้
- **Development build:** แอปทดสอบของโครงการเรา ใช้ทดสอบการแจ้งเตือนและส่วน native ที่ต้องตั้งค่าเฉพาะ
- **แอปเดโมที่ติดตั้งเองได้:** เตรียม Android build สำหรับติดตั้งและทดสอบก่อนวันนำเสนอ ผู้ใช้ไม่ต้องใช้ Expo Go

Expo Push Service บน Android ยังต้องมีการตั้งค่า credentials ของ FCM ตามคู่มือ ไม่ได้ใช้แทนการตั้งค่าฝั่งแพลตฟอร์มทั้งหมด ใช้ Firebase เฉพาะส่วนส่งแจ้งเตือนได้ ไม่ต้องเพิ่ม Firestore เป็นฐานข้อมูลชุดที่สอง

### สิ่งที่ต้องพร้อมก่อนเริ่ม

- Node.js รุ่นที่รองรับโดย Expo รุ่นที่เลือก, Git และ package manager หนึ่งตัว
- บัญชี Supabase, Expo และบัญชีที่จำเป็นสำหรับตั้งค่า FCM
- บัญชี AI API พร้อมงบใช้งานตามที่ทีมตกลง เก็บ secret ฝั่งเซิร์ฟเวอร์
- มือถือ Android สำหรับเดโมและอินเทอร์เน็ต
- บัญชีผู้ป่วยสมมติอย่างน้อย 2 คน และเจ้าหน้าที่ 1 คน
- ตรวจโควตา ค่าใช้จ่าย และเวลาสร้างแอปของบริการก่อนเริ่ม ไม่ตั้งสมมติฐานว่าทั้งหมดใช้ฟรีไม่จำกัด

### ตัดออกจาก 20 วันนี้

- เว็บเจ้าหน้าที่แยกอีกโปรเจกต์ และ iOS
- สมัครสมาชิกด้วยตนเอง ลืมรหัสผ่าน และขั้นตอนลงทะเบียนผู้ป่วยเต็มระบบ
- การรับคำสั่งเสียงและการฟังเสียงตลอดเวลา
- การถ่ายใบเสร็จ ฉลากยา ใบนัด และ OCR
- ตารางยา เตือนยา ประวัติกินยา และการแนะนำยา
- ระบบจองเวลาว่าง เลือกแพทย์ คิวสด และค้นหาโรงพยาบาลใกล้ที่สุด
- ผลตรวจ เวชระเบียนจริง และการตัดสินว่าผู้ป่วยกลับบ้านได้
- AI วินิจฉัยหรือแชตบอตตอบคำถามการแพทย์ทุกเรื่อง
- การเชื่อมระบบโรงพยาบาลจริงและหลายสถานพยาบาล
- บัญชีผู้ดูแล กราฟสุขภาพ คะแนน และประวัติซับซ้อน
- การเทรน AI เอง และระบบหลังบ้าน Java/Spring Boot เพิ่มเติม

เหตุผลหลัก: ลดงานที่ต้องเชื่อมระบบภายนอก ลดสิ่งที่ผู้สูงอายุต้องเรียนรู้ และให้ผู้พัฒนาหลักรวมงานได้ทัน

## 5. Login และสิทธิ์

```text
Login ด้วย Supabase Auth
           ↓
อ่านบทบาทของบัญชีที่ระบบกำหนด
           ├── patient → หน้าดูนัดของตนเอง
           └── staff   → หน้าจัดการนัด
```

- ไม่ดูบทบาทจากรูปแบบรหัสผ่าน และไม่ให้ผู้ใช้เลือกเป็นเจ้าหน้าที่เอง
- ผู้ดูแลโครงการกำหนดบทบาทของบัญชีเดโมไว้ล่วงหน้า
- ถ้าไม่พบบทบาทหรืออ่านข้อมูลไม่สำเร็จ ต้องไม่เปิดหน้าเจ้าหน้าที่
- ซ่อนหน้าหรือปุ่มอย่างเดียวไม่พอ ฐานข้อมูลต้องตรวจสิทธิ์ด้วย
- ผู้ป่วยอ่านได้เฉพาะนัดตนเอง และแก้ได้เฉพาะข้อมูลรับทราบผ่านช่องทางที่จำกัดสิทธิ์
- อย่าให้สิทธิ์ UPDATE ทั้งแถวเพียงเพื่อกดรับทราบ เพราะอาจทำให้แก้วันเวลาและคำแนะนำได้ด้วย ใช้ฟังก์ชันฐานข้อมูลที่ตรวจตัวตนและรุ่นนัด หรือจำกัดสิทธิ์ระดับคอลัมน์ร่วมกับ RLS
- ผู้ใช้ทั่วไปต้องแก้ role ของตนเองไม่ได้
- เมื่อสลับบัญชี ล้างข้อมูลผู้ใช้เก่าและปรับการผูกอุปกรณ์แจ้งเตือนให้ถูกคน

| รายละเอียดนัด | วัน เวลา สถานที่ แผนก และคำแนะนำจากเจ้าหน้าที่ |

| รายการนัดเจ้าหน้าที่ | รายการนัดและปุ่มสร้าง/แก้ไข/ยกเลิก |

หลักการ UX: ตัวอักษรใหญ่ ปุ่มใหญ่ สีตัดกัน ข้อความกำกับทุกปุ่ม แสดงวันที่เต็มพร้อมเวลา ไม่พึ่งสีหรือเสียงอย่างเดียว และไม่รวมข้อมูลหลายประเภทในหน้าแรก

## 7. บทบาทของกรร

คำถามเป้าหมาย:

1. นัดครั้งหน้าเมื่อไร?
2. ต้องไปที่ไหน?
3. ต้องเตรียมอะไรบ้าง?

ขั้นตอน: แอปส่งคำถาม → เซิร์ฟเวอร์ตรวจ session → ดึงเฉพาะนัดที่ผู้ใช้มีสิทธิ์อ่าน → ส่งบริบทที่จำเป็นให้ AI → คืนคำตอบ

- ไม่รับ patient_id จากแอปแล้วเชื่อทันที ต้องผูกกับตัวตนที่ผ่านการตรวจสอบ
- ไม่ให้ AI เข้าถึงฐานข้อมูลทั้งหมดหรือใช้ AI เป็นผู้ตัดสินสิทธิ์
- ถ้าไม่มีคำแนะนำก่อนนัด ให้บอกว่าไม่มีข้อมูลระบุไว้ ไม่เติมเรื่องงดน้ำหรืออาหารเอง
- AI ไม่มีสิทธิ์สร้าง แก้ไข หรือยกเลิกนัดในรุ่นนี้
- หาก AI ใช้งานไม่ได้ ผู้ใช้ยังดูและฟังข้อมูลนัดตรงจากระบบได้
- ปุ่มฟังรายละเอียดอ่านข้อมูลนัดโดยตรง ไม่จำเป็นต้องผ่านคำตอบ AI
- การแสดงและเตือนนัดไม่ใช่ AI คุณค่าของกรรอยู่ที่การตอบคำถามภาษาธรรมชาติจากข้อมูลที่ถูกต้อง

## 8. โครงสร้างโฟลเดอร์ล่าสุด

```text
checkin/
├── mobile/                         # แอปเดียว มีสองบทบาท
│   ├── app/
│   │   ├── _layout.tsx             # session และการเข้าถึงหน้า
│   │   ├── index.tsx               # ส่งไปหน้าตาม role
│   │   ├── login.tsx
│   │   ├── patient/
│   │   │   ├── index.tsx           # นัดครั้งถัดไป
│   │   │   ├── appointments/
│   │   │   │   └── [id].tsx        # รายละเอียดและรับทราบนัด
│   │   │   └── assistant.tsx
│   │   └── staff/
│   │       ├── index.tsx           # รายการนัด
```

## 9. โครงสร้างข้อมูลเริ่มต้น

| ตาราง | ข้อมูลหลัก |
|---|---|
| profiles | id ที่อ้างถึง Auth, ชื่อแสดงผล, role |
| appointments | id, patient_id, วันเวลานัด, สถานที่, แผนก, คำแนะนำ, status, version, acknowledged_version, acknowledged_at, created_by, updated_at |
| device_tokens | user_id, push_token, platform และสถานะใช้งาน |
| notification_deliveries | appointment_id, appointment_version, ประเภทการเตือน, อุปกรณ์, สถานะส่ง และเวลาส่ง |

- ใช้ Supabase Auth เก็บบัญชีและรหัสผ่าน
- เก็บเวลานัดด้วยชนิดที่รองรับเขตเวลา และแสดงผล Asia/Bangkok
- เมื่อรายละเอียดสำคัญเปลี่ยน เพิ่ม version และให้รับทราบใหม่
- งานส่งเตือนตรวจสถานะและ version ล่าสุดก่อนส่ง ไม่ส่งนัดที่ยกเลิก
- กำหนดเงื่อนไขกันส่งซ้ำตามนัด รุ่นนัด ประเภทการเตือน และอุปกรณ์
- การส่งออกสำเร็จไม่ได้ยืนยันว่าผู้ป่วยเห็นแจ้งเตือนแล้ว และการรับทราบไม่ได้ยืนยันว่ามาถึงโรงพยาบาล
- ไม่นำ AI API key หรือกุญแจสิทธิ์สูงของ Supabase ใส่ในแอปหรือ Git

## 13. บทเดโม

1. Login เป็นเจ้าหน้าที่ สร้างนัดให้ผู้ป่วยสมมติ
2. Login ฝั่งผู้ป่วยบนอีกเครื่องหรือสลับบัญชี แสดงนัดใหม่
3. กดฟังรายละเอียดและรับทราบ
4. ถามกรรว่า “ต้องเตรียมอะไรบ้าง” ให้ตอบตรงกับคำแนะนำในนัด
5. เจ้าหน้าที่เลื่อนนัด ผู้ป่วยเปิดข้อมูลล่าสุดและรับทราบใหม่
6. สาธิตการเตือนด้วยนัดเวลาสั้น โดยบอกชัดว่าเร่งเวลาสำหรับเดโม

ประโยคนำเสนอ:

> “Checkin ช่วยให้ผู้สูงอายุเข้าถึงข้อมูลนัดหมายได้ง่าย เจ้าหน้าที่เป็นผู้ระบุนัด ผู้ป่วยเปิดดู รับการเตือน และถามกรรได้ว่าต้องไปเมื่อไร ที่ไหน และเตรียมอะไร โดยไม่ต้องกรอกข้อมูลเอง”

## 14. สิ่งที่ยังต้องตัดสินใจและแผนต่อยอด

ก่อนเริ่ม: จำนวนคน เวลาว่างต่อวัน เครื่อง Android ที่ใช้เดโม ผู้รับผิดชอบแต่ละงาน ผู้ให้บริการ AI และงบ API รวมถึงเกณฑ์และเวลาส่งงานจริง ภาพหัวข้อการแข่งขันยังไม่ใช่รายละเอียดกติกาทั้งหมด

หลัง Hackathon: คุยกับสถานพยาบาลหนึ่งแห่ง → ตรวจขั้นตอนนัดจริงและการยืนยันตัวผู้ป่วย → ขอช่องทางเชื่อมข้อมูลเพื่อลดการกรอกซ้ำ → ทดลองกับผู้ใช้ → พิจารณาเสียงสั่งงาน บัญชีผู้ดูแล และตารางยาในระยะถัดไป
